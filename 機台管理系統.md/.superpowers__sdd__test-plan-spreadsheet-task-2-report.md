## GREEN evidence

The editor now dynamically loads ExcelJS and SheetJS together for `.xlsx`, retains `spreadsheet.SSF.format` in a ref, and uses `formatSpreadsheetNumber` for numeric values and numeric formula results. Existing formula-input behavior remains on `readFormattedFormulaValue`.

The row/column actions are labelled `向下插入列` and `向右插入欄`. They calculate a merge-safe insertion boundary, copy only neighbouring cell styles plus row height or column width, clear inserted values, reapply shifted ExcelJS merge ranges, mark the workbook structurally dirty, and reveal the inserted cell.

For legacy sheets, affected address-keyed cells shift in descending order. `!ref`, `!rows`, `!cols`, and `!merges` receive the same insertion offset while formula/value/style objects remain intact.

## Review follow-up: executable workbook insertion coverage

### Review findings addressed

1. **Critical — formatted merged-cell styles:** `spreadsheetWorkbook.ts` snapshots every cell style in every formatted merge before `unMergeCells`, shifts the snapshots with the merge, re-merges, and restores the shifted styles. This prevents ExcelJS unmerge/remerge from discarding merge-cell formatting.
2. **Important — legacy inserted styles:** legacy row/column insertion now creates `{ t: "z", s: clonedStyle }` cells for every adjacent source cell with a style. The created cells have no value or formula, while row height and column width metadata still shift separately.
3. **Important — runtime coverage:** `spreadsheet-workbook.test.ts` imports and mutates real ExcelJS and SheetJS workbooks rather than inspecting source text.

### RED evidence

First, with the runtime tests written before the module existed:

```text
node --test tests/test-plan/spreadsheet-workbook.test.ts
# 0 passed, 3 failed
```

All three failures were the expected `spreadsheet workbook mutations must be available` assertion because the new mutation module did not yet exist.

After the first implementation attempt, Node reported `ERR_MODULE_NOT_FOUND` for the extensionless nested import. The root cause was Node's native TypeScript module resolver; adding the explicit `.ts` suffix to the module's dependency fixed loading without changing browser bundling behavior. The runtime test then exposed an invalid fixture expectation: Task 1 correctly advanced an insertion past a merge located at the first candidate boundary. The fixture was moved beyond that boundary so it tests a shifted merge without asking the code to split one.
