# BOM 版本控制與新舊版差異設計

日期：2026-10-29。範圍：料號申請工作區的 BOM 管理。既有黑底青綠風格、共用 Dialog／Button／Select／Table、持久篩選契約與 CE 15 欄交付格式全部沿用。

## 問題

- 目前 BOM 的識別碼由檔名產生（`bom:<檔名 slug>`）。同檔名重新上傳會直接覆蓋原 BOM；不同檔名則變成一份毫無關聯的新 BOM。兩種情況都沒有保留舊內容，也沒有任何差異紀錄。
- 料件 id 是「工作表＋列號」。CE 在新版 Excel 插入或刪除一列，列號之後的追蹤紀錄會全部接到錯的料件上；工作表改名則整份追蹤消失。
- 檔名 slug 只保留 `a-z0-9`，`主板.xlsx` 與 `電源板.xlsx` 都變成 `bom:xlsx`，會互相覆蓋。
- 工廠拿到新版 BOM 時，沒有人能回答「跟上一版差在哪裡」。這是給工廠錯料的直接來源。

## 目標

1. 每次上傳都是獨立、不可被覆蓋的版本快照；同一塊板的版本收在同一個「BOM 系列」下，只有一個「目前版本」。
2. 任兩個版本可以比對，差異以工廠看得懂的方式分類：新增、移除、位號、數量、主料、替代料、狀態、規格／文字，並可匯出 Excel。
3. 新版本上傳時，RD 在舊版維護的追蹤紀錄依「內容」而非「列號」帶到新版；帶不過去的料件明確列出，不再默默遺失。
4. 不新增資料庫 migration：沿用現有 `material_bom_workspaces`／`material_bom_records` 存版本內容，`ui_table_preferences` 存版本中繼資料，正式站推上 Pages 即可使用。
5. 不拖慢頁面：版本中繼資料是小筆 KV；舊版料件只在比對時載入，並且不覆寫目前使用中 BOM 的 IndexedDB 快取。

非目標：不改料件表的欄位與編輯流程；不改追蹤紀錄的資料形狀；不自動判定哪個版本「正確」，版本的採用由人決定。

## 資料模型

### 版本＝workspace

一個版本就是一個 `BomWorkspace`（既有結構）。料件、頁數、配色、專案、封存都維持原本的每 workspace 儲存方式。新版本的 id 不再由檔名推導，改為 `bom:<系列 slug>:v<N>:<6 位亂數>`，避免碰撞與覆蓋。

### 版本中繼資料（`ui_table_preferences`，key `material-bom-version:<workspaceId>`）

```ts
interface BomWorkspaceVersion {
  seriesId: string;            // "series:<uuid>"
  seriesName: string;          // 系列顯示名稱，每個版本都存一份，以最新寫入為準
  versionNumber: number;       // 建立時固定，不因刪除其他版本而改號
  label: string;               // 版本標籤，例如 EVT rev B
  note: string;                // 版本說明／改版原因
  uploadedAt: string;
  uploadedBy: string;
  previousWorkspaceId?: string; // 上傳時對照的版本（追蹤帶入來源）
  isCurrent: boolean;
  currentChangedAt: string;    // 解析多個 isCurrent 時以最新者為準
  carry?: { matched: number; orphaned: number; manual: number }; // 追蹤帶入摘要
  source?: { name: string; path: string; size: number; mimeType: string }; // 原始 Excel（可選）
}
```

- 沒有版本列的既有 BOM 視為「單一版本系列」：`seriesId` 等於 workspace id、版本 1、目前版本。第一次對它上傳新版本時，才同時為舊 workspace 補寫版本列。
- 目前版本的判定：同系列中 `isCurrent` 為真者取 `currentChangedAt` 最新；若沒有，取版本號最大者。版本號若因同時上傳而重複，顯示時以上傳時間排序並加註。
- 系列層級的屬性（名稱、專案、封存）寫到該系列每一個版本的既有 key，讀取時以目前版本為準。這讓切換器、分組、封存區等既有邏輯不必知道系列。
- 原始 Excel 以既有 `material-spec-documents` bucket 保存於 `<workspaceId>/_source/<時間>-<檔名>`，沿用 SPEC 的簽名網址下載；上傳失敗不阻止建立版本，但在版本列註記「原檔未保存」。
- 即時同步：版本 key 加入既有 `BOM_PREFERENCE_KEY_PREFIXES`，其他人改版本、改目前版本時，透過現有的 preference 通知重新讀取中繼資料。

### 讀取與快取

- 新增 `loadBomWorkspaceRecords(workspaceId)`：只抓該版本的料件，走既有分段並行讀取，不寫 IndexedDB 快取，不改 active workspace。比對視窗用它載入舊版，載入結果在視窗存活期間記憶體快取。
- `saveBomWorkspace` 找舊列時的 `select("record_id")` 改為分頁讀取，避免 PostgREST 預設 1000 列上限漏刪舊列。

## 配對與差異規則（`bomDiff.ts`，純函式）

### 料件群組

- 位號 token：以逗號、空白、分號切開，NFKC、去空白、大寫；`-` 與空字串忽略。
- 群組 key：位號 token 排序後以 `|` 連接。沒有位號的列退回 `虛擬料號` → `實體料號` → `廠商+MPN` → `料名+規格`，並加 `noref:` 前綴。
- 同一版本中 key 相同的列合併為同一群組；群組內的列順序保留，第一列視為主料。

### 群組配對（舊 → 新）

1. key 完全相同者先配對。
2. 其餘群組以位號 token 重疊數配對：對每個新群組找重疊最多的舊群組，重疊數需 ≥ 1 且為雙方最佳（貪婪、重疊數大者優先）。配對成功代表同一設計位置，只是位號增減（例如 `C101,C102` → `C101,C102,C103`）。
3. 沒配到的新群組＝新增，舊群組＝移除。

### 廠商明細配對（群組內）

依序以 `實體料號`（正規化）→ `廠商+MPN` → `MPN` 配對；剩下的是替代料新增／移除。

### 欄位比較與分類

比較欄位：Name、Qty、Ref Des、Manufacturer、MPN、Sourcing Status、虛擬料號、實體料號、Part Name、Part Spec、Schematic_Part、PCB_Footprint、phase out、零件狀態；另記錄系統／模組分組變更。文字比較前做 NFKC、去頭尾空白；數量以數值比較。

變更類型（一個群組可同時有多種）：

| 類型 | 條件 | 影響層級 |
| --- | --- | --- |
| 新增 | 新版才有的群組 | 生產 |
| 移除 | 舊版才有的群組 | 生產 |
| 位號 | 位號 token 增減 | 生產 |
| 數量 | Qty 數值不同 | 生產 |
| 主料 | 群組第一列的實體料號／MPN 不同 | 生產 |
| 替代料 | 廠商明細新增或移除 | 生產 |
| 狀態 | Sourcing Status、phase out、零件狀態不同 | 狀態 |
| 規格 | Name、Part Name、Part Spec、Schematic_Part、PCB_Footprint、虛擬料號、分組不同 | 文字 |

影響層級取最嚴重者：生產 > 狀態 > 文字。只有位置不同（列序調動）的料件視為未變更。

### 追蹤帶入（`carryTracking`）

- 用同一套配對把舊版料件的 `trackingStatus`、`trackingHistory`、`trackingNote`、`requestTicket`、`requestUrl`、`specDocument`、`pendingCategory`、`remark` 複製到新版配對到的列；新版 Excel 若自己帶了匯入追蹤，匯入追蹤排在前、舊手動紀錄保留在後（與現行 `mergeTrackingHistories` 相同）。
- 舊版 `manual-` 開頭的手動料件整列複製到新版（沿用現行行為）。
- 有追蹤內容但沒配對到的舊列記為 `orphaned`，差異檢視與版本列都看得到數量，並可在差異表中以「追蹤未帶入」篩選。舊版本身完整保留，紀錄不會消失。

## 上傳流程

1. 「上傳 BOM」照舊選檔（可多檔）；解析後不再直接寫入，而是開啟「上傳確認」視窗。
2. 每個檔案一列：來源檔、工作表、筆數、匯入注意事項，以及目標選擇「建立新 BOM 系列」或「作為〈系列〉的新版本（目前 V3）」。預選規則：來源檔名與某系列任一版本相同 → 該系列；去掉版本／日期尾綴後的 slug 相同 → 該系列；否則新系列，系列名稱預設為去副檔名的檔名。
3. 可填版本標籤與版本說明（多檔共用）。新系列歸入目前專案（與現行相同）；新版本沿用系列的專案、配色與頁數。
4. 確認後逐檔建立版本：先存料件（含追蹤帶入），再寫版本中繼資料（新版 `isCurrent: true`，舊的目前版本 `isCurrent: false`），最後保存原檔。版本中繼資料寫入前以寫入範圍（既有 `captureBomWrite`）確認帳號與權限未變。
5. 完成後切換到新版本；若有追蹤未帶入，toast 直接說明數量並指向差異檢視。
6. 版本中心每個系列有「上傳新版本」，點它等於上傳確認時已鎖定該系列。

## 視窗設計（`BomVersionCenter`）

取代現有單層清單的 BOM 管理視窗。桌面為兩欄（`min(96vw,1500px)` × `min(92vh,900px)`）：

- 左欄「BOM 系列」：搜尋列在結果正上方；依專案分組（目前專案優先、未指定最後，沿用 `groupBomWorkspacesByProject`）；每列顯示系列名、目前版本號、版本數、筆數、更新時間、使用中／含追蹤／歷史檢視中標籤；底部為可展開的封存區。
- 右欄「系列詳情」：系列名稱（可改）、專案 Select、主動作「上傳新版本」，次動作「比對版本」「封存系列」，破壞性「刪除系列」在最後；版本時間軸表格：版本、標籤、來源檔、筆數、上傳時間／人、說明、追蹤帶入、狀態、操作（檢視、設為目前版本、頁數、原檔、刪除版本）；下方是「目前版本 vs 前一版」的差異摘要卡與「開啟完整差異」。
- 差異模式：占滿視窗。上方「返回系列」、舊版／新版 Select 與「交換」；KPI 列（新增／移除／變更／未變更、各類型數量）；持久篩選列（搜尋 → 變更類型 → 影響 → 追蹤未帶入），作用中條件以 chip 顯示、可個別清除與全部清除；表格欄位：位號、料名、變更類型、影響、舊、新、廠商明細、追蹤；空結果保留表頭並顯示「目前篩選條件沒有符合的差異」；「匯出差異 Excel」在工具區尾端。
- 1023px 以下：左右欄改為堆疊，選系列後進入詳情並有「返回清單」；差異表容器橫向捲動，chip 可換行，所有按鈕維持 44px 命中區。
- 歷史版本：料號頁上方出現常駐提示「正在檢視〈系列〉V2（歷史版本），目前版本為 V3」，附「回到目前版本」。歷史版本唯讀：不可新增／修改料件與追蹤、不可上傳。版本中心的操作仍可用。
- 刪除：刪除歷史版本要確認並指出版本；目前版本在系列還有其他版本時不可刪，必須先設定其他版本為目前版本；刪除系列列出版本數與筆數。

## 匯出差異 Excel（`bomDiffExport.ts`，ExcelJS）

- 工作表「摘要」：系列、舊版／新版（版本、標籤、來源檔、上傳時間）、各類型數量、匯出人與時間。
- 工作表「差異明細」：一列一個欄位變更：位號、料名、變更類型、影響、欄位、舊值、新值、廠商、MPN、實體料號。新增／移除群組的每個廠商明細各一列，欄位寫「整列」。
- 工作表「新增料件」「移除料件」：完整 CE 15 欄，供工廠直接核對。
- 檔名 `BOM差異_<系列>_V<舊>_vs_V<新>_<時間>.xlsx`。

## 權限與安全

- 版本中心的寫入沿用 `useWorkspaceMutationScope`：模組編輯權限與帳號在非同步期間改變即中止，不寫入。
- 料件層級的 `canEdit` 另外加上「目前版本」條件；歷史版本的所有料件操作為唯讀。
- 原檔下載走簽名網址（60 分鐘），bucket 仍為私有。
- 審計：版本建立、設為目前版本、刪除版本沿用 `logMaterialWorkspaceAction`，metadata 帶系列與版本號。

## 相容與遷移

- 既有 6 份 BOM 不需搬資料：缺版本列即視為單一版本系列，畫面與今天相同。
- 現行「同檔名更新原 BOM」行為移除；上傳說明與 FAQ 改為「同一塊板再上傳即成為新版本」。
- 測試用 mock（`tests/support/materialWorkspaceMock.js`）補上版本中繼資料與第二個版本，讓隔離頁面能走完整流程。

## 風險與對策

- 位號重疊配對可能把兩個都改動的群組配錯：只在重疊數為雙方最佳時配對；配對結果在差異表可展開看到舊／新位號。
- 多人同時上傳同系列：版本號可能重複，顯示時以時間排序並標示；目前版本以 `currentChangedAt` 解析。
- 大 BOM（7,000 列）兩版比對：純函式用 Map 索引，複雜度接近線性；在隔離頁以 2×7,000 列量測需在 200ms 內。
- 原檔保存依賴既有 bucket；bucket 不存在時只影響原檔下載，不影響版本功能。

## 驗證

- 純函式測試：群組配對（完全相同、位號增減、無位號退回鍵）、廠商配對（實體料號、廠商+MPN、MPN）、各變更類型、列序調動不算變更、追蹤帶入與 orphan、系列推斷、版本號、目前版本解析。
- 匯出測試：ExcelJS 產物工作表與欄位。
- 來源契約測試：版本中心的篩選列、chip、空結果文字、刪除確認、歷史唯讀提示。
- 隔離瀏覽器頁：兩個版本的 QA 資料，走上傳確認、比對、匯出、設為目前版本、桌面與 390px 截圖。
- `npm run typecheck`、`npm run lint`、`npm test`、`node --test tests/audit*.integration.cjs`、`npm run build`，推送後核對 Pages 部署。
