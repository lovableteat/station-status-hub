# 網站載入速度（2026-11-21）

使用者回報：「網站許多地方開啟速度太慢，希望大幅降低，請優化整個網站載入時間及速度」。本文件記錄量到的原因、改了什麼、怎麼再量一次，以及之後改程式時要守住的規則。

## 量到的原因

量測方式見最後一節。四個原因都先用量測或程式路徑確認，再動手改。

1. **啟動是一關一關排隊。** 進入頁 → 驗證登入 → 外殼（`AuthenticatedApplication`）→ 首頁（`Index`）→ 權限 → 工作區，每一關的程式檔都要等前一關跑完才知道要下載；每一關至少一次網路來回。React 在巢狀 Suspense 一層一層顯示時，還會把後面的顯示往後壓（fallback throttle），外殼裡各 Provider 的第一批資料請求也跟著晚出發。
2. **每個人一開站都載入維修中心的舊測試資料。** `UnifiedDataProvider` 掛在所有工作區上面，一啟動就把 `test_systems`、`test_flow_stations`、`test_flow_items`、`station_contents`、`test_progress` 五張表整批抓下來（`select *`、逐頁抓完），並訂閱五張表的即時更新；每次視窗重新取得焦點、網路恢復、即時連線重連都會整批重抓。實際讀這些資料的只有舊的 `/test-tracker` 頁面；`Index` 只用它的 `isUpdating` 顯示指示燈，卻因此每次重抓都跟著重新繪製目前的工作區。
3. **每次部署幾乎所有程式檔都換檔名。** 檔名帶內容雜湊，而內容裡寫著它引用的檔名。Rollup 把進入頁需要的共用程式都放進進入頁那一個檔，其他檔全都引用它；進入頁又（透過延遲載入）寫著每一個頁面的檔名，所以任何地方改一行，進入頁就換名，連帶幾乎全部檔案換名。實測只改三個檔，159 個程式檔有 126 個換名，包含完全沒改的 exceljs、three.js、jsPDF。每次部署後，使用者等於整個網站重新下載一次。
4. **切換工作區才開始下載那個工作區的程式。** 第一次切過去要等 0.3–0.8 秒（手機條件 0.6–2 秒）的下載。

沒有改的部分：Data-center 一開就下載兩個 3D 模型（約 6.4 MB），那是場景本身的內容，手機已有較小的 `.mobile.glb`；料號申請頁已有本機快取與每 3 秒的增量同步，資料面沒有動。

## 改了什麼

- **啟動需要的檔案同時下載**（`scripts/bootPreloadPlugin.ts`）。建置時把「外殼、首頁、每個工作區各需要哪些檔案」寫進 `index.html`，一小段內嵌程式在進入頁還在下載時就用 `<link rel="modulepreload">` 一起要。這個分頁已有登入階段時立刻要；未登入時等登入頁顯示完、瀏覽器閒置才要（只要程式檔，不要樣式表），這樣按下登入後等的只有驗證。2G 與省流量模式下，未登入時不預先下載。
  - 內嵌程式緊接在 `<meta charset>` 後面：放在樣式表連結後面的內嵌程式要等樣式表下載完才執行，預先下載就不是「同時」了；也不能放在編碼宣告前面，瀏覽器只在前 1024 個位元組找它（兩點都是獨立檢查指出）。
  - `modulepreload` 只下載與編譯，不執行。私有外殼仍然只在登入驗證通過後才 `import()` 與顯示（`tests/authenticatedApplicationLoading.test.mjs` 不變）。這些檔本來就是任何人都能下載的公開靜態檔。
- **外殼一次顯示**（`src/App.tsx`、`AuthenticatedApplication.tsx`、`Index.tsx`）。外殼的延遲載入會等首頁的程式也載好（最多等 2.5 秒）才交給 React，所以只有一次顯示，不再一層一層被往後壓；網址指定的工作區也在這時開始載入，不等權限查完（能不能顯示仍由 `PermissionGuard` 決定）。
- **其他工作區在閒置時先下載好**（`src/lib/idlePreload.ts`）。權限查完、畫面穩定 3 秒後，一次一個工作區、在瀏覽器閒置時下載這個帳號能開的其他工作區的程式。只下載、不執行（同樣用 `modulepreload`，由內嵌程式留下的 `window.__STATION_PRELOAD__(key)` 處理），程式等真的打開那個工作區才執行，也不抓任何工作區資料。這些背景下載設成低優先權（`fetchPriority = "low"`），不跟畫面上正在用的請求搶頻寬。第一版用 `import()`，會把別的工作區的程式直接執行，權限多的帳號要載 1.4 MB，手機上可能卡頓（獨立檢查指出），所以改掉。
  - 不做的情況：2G／3G、省流量模式；以及瀏覽器不回報連線種類的觸控裝置（iPhone、iPad 的 Safari），因為那可能是行動網路。電腦上的 Safari／Firefox 同樣不回報，但照常預先下載。
- **舊測試資料改成有人讀才載入**（`src/hooks/useUnifiedData.ts`）。`useUnifiedData()` 的讀取者掛上時才抓資料、訂閱；最後一個讀取者離開就關閉訂閱並清掉資料。`Index` 改用 `useUnifiedData({ demand: false })`，只看狀態，不觸發載入。
- **部署只換有改到的檔名**（`scripts/stableChunks.ts`）。三個含延遲載入的模組（進入頁、外殼、首頁）各自一個小檔，原本和它們放在一起的東西分別放進 `core`、`shell`、`home` 三個不含任何頁面檔名的檔。沒有任何檔案靜態引用那三個小檔，所以改一個工作區只會讓那個工作區和三個小檔換名。
  - 做法是建置兩次：第一次照 Rollup 原本的分法（不寫檔、不壓縮），記下每個模組被分到哪個檔；第二次告訴 Rollup「每個模組照第一次的分法」，只有三個樞紐模組不指定，讓它們自己成檔。建置時間約多 25 秒。
  - 只指定三層是不行的（試過兩次）：Rollup 的 `manualChunks` 會把被指定模組的所有靜態相依一起拉進同一個檔，而 `import { Bell } from "lucide-react"` 經過套件的索引檔會連到每一個圖示，結果全站 259 個圖示都進了登入頁要載的檔（多 21 KB），而且某個頁面新用一個圖示就又整批換名。
  - 另外關掉 `minifyInternalExports`：Rollup 給跨檔匯出取的短名字（a、b、c…）是照「其他檔第一次用到的順序」排的，某個頁面多引用一個東西就會讓 `core` 裡的名字重排、全部換名（實測：頁面新用一個圖示，251 個檔有 129 個換名）。改用原本的名字後整體大小多 0.5%。
  - 驗證（用專案鎖定的套件版本建置）：`core` 329 KB／gzip 108 KB，與原本的進入頁檔案（329／107）相同；163 個程式檔沒有任何一個靜態引用樞紐。改一個料號申請的檔案三種改法（改文字、新用一個圖示、新引用一個共用元件），都是 251 個檔只有 7 個換名：那個工作區和它的 3 個子檔，加三個樞紐。

## 量測結果（2026-11-21）

用專案鎖定的套件版本建置修改前與修改後兩個版本，同一套假資料、同樣的限速。cold 與 warm 是 3 次的中位數，單位毫秒。

電腦、辦公室網路（延遲 60 ms、20 Mbps）：

| 頁面 | 第一次開（cold）前 → 後 | 待在首頁一陣子後切過去（afterIdle）前 → 後 |
|---|---|---|
| 首頁 | 919 → 679 | — |
| 維修中心 | 1080 → 687 | 285 → 195 |
| 檔案上傳 | 1523 → 1005 | 724 → 401 |
| 比對系統 | 1394 → 866 | 594 → 204 |
| 料號申請 | 1523 → 994 | 773 → 482 |
| Data-center | 2186 → 1661 | 2612 → 1076 |
| PCB Designer | 1278 → 801 | 495 → 196 |
| AI 問答 | 1218 → 773 | 441 → 190 |
| 績效考核 | 1284 → 792 | 541 → 296 |
| 後台管理 | 1384 → 862 | 639 → 228 |

手機條件（延遲 150 ms、5 Mbps、CPU 放慢 4 倍）：

| 頁面 | 第一次開（cold）前 → 後 | 待在首頁一陣子後切過去（afterIdle）前 → 後 |
|---|---|---|
| 首頁 | 2220 → 1946 | — |
| 維修中心 | 2475 → 1888 | 585 → 420 |
| 檔案上傳 | 3026 → 2256 | 1396 → 716 |
| 比對系統 | 2837 → 2011 | 1186 → 358 |
| 料號申請 | 3308 → 2508 | 1674 → 1000 |
| Data-center | 5061 → 4155 | 3924 → 3735 |
| PCB Designer | 2906 → 2158 | 1273 → 527 |
| AI 問答 | 2752 → 1894 | 1075 → 450 |
| 績效考核 | 3195 → 2590 | 1519 → 1015 |
| 後台管理 | 3091 → 2254 | 1470 → 618 |

- 第一次開：電腦快 24–38%，手機條件快 12–31%。
- 待一陣子後切換工作區：電腦快 31–66%，手機條件快 5–70%（Data-center 幾乎沒變，時間花在 3D 模型）。
- 啟動時的資料請求：首頁 13 個 → 8 個（少掉舊測試資料的五張表）。
- 沒有變快的：同一個分頁重新整理（warm，電腦約 0.4–0.6 秒、手機條件 0.7–1 秒）。那段時間是「驗證登入 → 權限與外殼資料 → 工作區資料」一個接一個的資料請求，這次沒有動。剛進首頁就立刻切換工作區（背景還沒下載完）也和以前一樣。
- 部署之後：改一個工作區的檔案，251 個檔只有 7 個換名（以前幾乎全部）。使用者部署後第一次開，只需重新下載有改的部分。

## 之後改程式要守住的規則

- 新增工作區或維修中心模組：在 `scripts/bootPreloadPlugin.ts` 的 `BOOT_PRELOAD_MODULES` 加一筆，並在內嵌的網址判斷 `BOOT_PRELOAD_KEY_SOURCE` 加上對應規則。`tests/bootPreload.test.mjs` 會拿 `Index.tsx` 的 `getInitialWorkspace`／`getInitialStationModule` 逐一比對，漏了會失敗。
- 延遲載入（`import()`）頁面的程式只放在三個樞紐模組：`App.tsx`、`AuthenticatedApplication.tsx`、`pages/Index.tsx`。在它們靜態引用到的共用模組裡加 `import()`，會讓 `core`／`shell`／`home` 寫進頁面檔名，部署後又整批換名（`tests/bootPreload.test.mjs` 會掃描並擋下）。建置時若看到 `stable chunks:` 開頭的警告，表示分檔退回了舊的方式或有檔案引用了樞紐，要處理。
- 掛在所有工作區上面的 Provider 不要在啟動時抓只有少數頁面要用的資料；照 `useUnifiedData` 的做法，有讀取者才載入。
- 背景預先載入只能下載程式（不執行、不抓資料），也不能用計時器搶在目前畫面的第一次顯示之前（`tests/stationStatusPerformance.test.mjs` 的舊教訓）。只有使用者真的切換工作區時才 `import()`。

## 怎麼量

```bash
node scripts/perf/build.mjs current
```

```bash
AUDIT_QA_DIR=../qa-tools node scripts/perf/measure.cjs current office
```

- `scripts/perf/build.mjs` 用正式的 `vite.config.ts` 建置，只把 Supabase client 換成 `scripts/perf/startupMock.mjs`：手機稽核用的隔離假資料，加上一個已登入的階段，每個資料請求固定延遲 80 ms，並記錄每個請求的起訖時間。沒有任何真實帳號或資料。
- `scripts/perf/measure.cjs` 用本機伺服器模擬 GitHub Pages 的標頭（`max-age=600`、gzip、ETag），在 Chrome 裡限速後量每個工作區。`office`：延遲 60 ms、20 Mbps（從這台電腦到 GitHub Pages 實測的量級）；`phone`：延遲 150 ms、5 Mbps、CPU 放慢 4 倍。
- 量的是程式載入與請求排隊的固定成本。假資料很小，所以真實資料的下載與查詢時間不在裡面；正式站需要登入，沒有辦法從外面量。
- 量測時不要同時跑建置或測試，CPU 被佔用會讓數字失真。每個頁面的 cold／warm 取 3 次的中位數（`PERF_RUNS`）。
- 本機的 `node_modules` 若比 `package-lock.json` 舊（2026-11-21 時 Vite 6.4.3 對 6.4.6、React Router 6.27 對 7.18.5），量出來的不是正式站會用的程式。當時是另開一個乾淨的 worktree 執行 `npm ci --legacy-peer-deps` 來建置與量測。
