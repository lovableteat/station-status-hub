## Why promotion must be staged

Do not copy all pending SQL files into `supabase/migrations` and run a bulk push. That would remove the verification pause between authorization changes and private-bucket cutover. Promote only the next separately approved stage after its prerequisites pass. Keep later stages outside the migration directory until their own gate is satisfied.

For already-applied versions `20261112001122`, `20261112013540` and `20261112022029`, preserve each exact existing version, name and statement bytes. Their immutable original preparation comments are historical, not current deployment status. Confirm the target ledger matches and skip each existing entry; do not manufacture duplicate versions, rerun pre-cutover guards, or repair the ledger merely to bypass a mismatch.

Before assigning each **new** migration timestamp, fetch current main and the actual target migration ledger. The next filename must follow the real latest migration, not the date this proposal was written. Compare source hashes, function definitions, owners/ACLs, policies, bucket settings and default privileges against a fresh target inventory. The old snapshot is evidence of prior state, not evidence that production is unchanged now.

The exact migration runner and final SQL wrapper must be rehearsed in an isolated restore. Preserve transaction boundaries and SET LOCAL timeouts. Do not assume a runner's implicit transaction and the proposal's explicit BEGIN/COMMIT compose safely without testing. Record the migration only after a successful committed stage; never mark a failed or uncertain stage applied merely to unblock the next one.

## Failure, replay and active writers

- Each stage is transactional. The synthetic test injects a late failure and checks rows, objects, function definitions, policies, grants and default ACLs after ROLLBACK. This does not prove hosted Storage cache atomicity or live multi-session writer safety.
- A failed PostgreSQL transaction stays aborted until ROLLBACK or connection close. The runner must perform one of those immediately, otherwise locks can remain held.
- lock_timeout is per acquisition, and statement_timeout is per statement. A loop touching many tables can hold earlier locks through later work. There is no verified whole-stage duration bound and no claim of zero interruption.
- Stages 01 and 03 create named policies and reject duplicate replay. The station-only stage 02 can be repeated only with its exact hardened predecessors and drift checks; the narrow PCB candidate intentionally rejects duplicate replay. The old stage 02 is not part of the new sequence. After a lost response or timeout, inspect the committed policy/ACL state and migration ledger before deciding to retry. Never blindly rerun a stage or automatically reopen anonymous access.
- Recovery starts from all three applied narrow cutovers, including login_audit anonymous denial. The old private pre-cutover whole-configuration rollback is retired/fail-closed, not a current executable plan; its historical bytes remain retained. Never regrant anonymous access from that snapshot. Once the PCB candidate is applied, its twelve guarded definitions/ACLs become part of the recovery baseline. The PCB rollback entry point is also retired/fail-closed. Fix compatibility forward rather than restoring its vulnerable preimage.
- For a compatibility failure, prefer a narrowly reviewed correction that retains the anonymous boundary. Do not revert all grants or public bucket settings automatically, and do not overwrite current rows to match an earlier snapshot.

## Future default privileges

The saved inventory showed postgres-owned schema defaults granting anon access in public/workspace. Stage 01 removes those specific anon defaults for future tables, sequences and functions, and PUBLIC table/sequence defaults in those two schemas. Other creators and schemas must be inventoried; this change does not claim to rewrite every managed owner's defaults.

PostgreSQL independently grants PUBLIC EXECUTE globally on new functions. A schema-specific REVOKE cannot cancel that global default. This proposal intentionally does not make a wider global default change, which could break future functions in unrelated schemas. Every future exposed function migration must revoke PUBLIC/anon and assign its reviewed caller roles in the same transaction before commit. Gate deployment on post-migration anonymous-ACL checks and reject any newly exposed non-allowlisted function. A global-default strategy requires separately reviewed scope and compatibility tests; do not claim the schema-specific change alone prevents all future RPC exposure.

## PCB sequence compatibility

The four old PCB replacements consist of two owner-only permission helpers and two callable lock-release/locked-save bodies. The narrow candidate changes neither helper and preserves the complete original twelve callable bodies except for the same first actor guard. Applying old stage 02 afterward would replace two of those guarded bodies and alter the locked-save contract. The station-only successor omits all four PCB replacements and their revoke block, preserving the narrowed candidate's behavior exactly. Both directions of incompatible ordering are tested to fail closed.

The synthetic integrated fixture verifies candidate → 01 → station-only 02 → 03, including all existing application/object rows, five fake legacy snapshots, the twelve hardened PCB definitions and ACLs, positive shared/model/lock paths, and unauthorized rejection. Stage 03 intentionally changes only the two bucket visibility settings among stored rows. Hosted frontend/Auth, real Storage/CDN, backup restoration and concurrent-client release gates remain mandatory; passing this fixture does not approve production execution.
