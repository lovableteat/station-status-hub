# 跨電腦重建與交接

更新日期：2026-10-20。程式碼核對基準：`c6629250`，不是新電腦或正式服務的驗收證明。

## 1. 先分清楚三種移轉

| 目的 | 要帶走的內容 | 不會自動完成的事 |
| --- | --- | --- |
| 用現有網站 | 正式網址與自己的核准帳號 | 另一個瀏覽器的本機資料不會跟著登入出現 |
| 繼續維護原系統 | Git 原始碼、依賴鎖檔、對應環境設定與必要的受控存取 | Markdown 不是程式、資料庫或附件備份 |
| 建一套功能相似的新網站 | 本文件包、原始碼參考、自己的新 repo／Supabase／設定／測試資料 | 不沿用正式專案、帳號、ID、API 金鑰或真實公司資料 |

本次目的是第三種。先在隔離的新系統做出可用版本，再考慮是否需要經核准的資料移轉。不要為了試跑而接上原正式後端。

## 3. 在另一台電腦準備程式碼

文件整理時本機是 Node `v24.14.0`、npm `11.9.0`；隔離測試 workflow 使用 Node 24，Pages 建置 workflow 仍使用 Node 20。這是目前的相容性基線，並非 Node 最新版建議，也不代表本輪在全新電腦驗證過。

```powershell
git clone https://github.com/lovableteat/station-status-hub.git station-status-reference
cd station-status-reference
git status --short
git rev-parse HEAD
npm ci --legacy-peer-deps
```

如果要做獨立產品，先建立自己的 repo，確認 `git remote -v` 指向自己的目的地後，才做任何 commit／push。不要直接在參考 repo 的 `main` 推送新產品，也不要為了換來源而刪除唯一的 Git 歷史。

`package-lock.json` 與 `package.json` 一起移轉；不要只複製 `src`、忽略 `public/comparison`、設定、migration 或依賴版本。套件安裝若失敗，保留錯誤，先核對 Node/npm、鎖檔與網路，不用刪除鎖檔掩蓋問題。

## 4. 建立新後端，避免寫到原正式資料

1. 在自己的帳號／組織建立隔離的 Supabase 專案；確認 ref、URL、費用與存取權限。
2. 閱讀 `supabase/migrations` 的 schema 演進：早期檔案使用 `public`，後續搬到 `workspace`，另有依既有資料修復的歷史 migration。本次未做空白資料庫重建驗證，不能承諾直接重播全部 SQL 就能初始化。
3. 在新專案審核並測試需要的 table、index、RPC、RLS、trigger、Storage bucket 與 Realtime；移植時保留身分對應與最小權限，不直接套用固定正式 user/project UUID。
4. 新專案的 Data API 必須正確暴露 `workspace`，schema 的 grant 與 RLS 是兩層不同的控制；不能用 `GRANT ALL` 或關閉 RLS 代替授權設計。
5. 依 `supabase/functions` 與 `supabase/config.toml` 配置實際需要的 Edge Functions。登入、帳號管理／自助、每日統計與 API 功能不是只部署靜態前端就會出現。
6. 用自己的核准測試帳號建立初始管理身分，核對 `system_users`、Auth UID 對應、角色與權限。現有一般註冊流程不能當作自動取得管理權限的方法；不在文件提供預設管理員密碼或提升角色的捷徑。

正式舊系統的遷移只依 [正式環境遷移操作手冊](./supabase-production-migration-runbook.md)；其中的原專案 ref 與受控單檔修復紀錄是歷史操作背景，不是新專案的初始化命令。執行 CLI 前先看該版本 `--help`，本次未執行任何遠端 migration。

## 5. 環境設定：只寫自己的值

```powershell
if (-not (Test-Path -LiteralPath '.env')) {
  Copy-Item -LiteralPath '.env.example' -Destination '.env'
}
```

如果 `.env` 已存在，先保留／核對，不直接覆寫。以下是變數名稱與用途，不是可直接登入的設定：

| 變數 | 位置／用途 |
| --- | --- |
| `VITE_SUPABASE_URL` | 新 Supabase 專案 URL；前端可見 |
| `VITE_SUPABASE_ANON_KEY` | 此 repo 的相容名稱，填新專案適用的瀏覽器公開 key；不能放 service-role key |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | client 支援的替代名稱；現有 Pages workflow 仍讀取上一列的 secret 名稱 |
| `VITE_SUPABASE_SCHEMA` | 前端 schema，現行預設為 `workspace` |
| `VITE_REALTIME_COLLABORATION_V2` | 前端即時協作旗標；開啟不代表 publication／RLS 已正確設定 |
| `APP_DB_SCHEMA` | Edge Functions 使用的 schema 設定，現行預設 `workspace` |
| `SUPABASE_DB_SCHEMA` | keep-alive workflow 使用的 REST profile；不是前端變數 |
| `SUPABASE_SERVICE_ROLE_KEY` | 僅受控伺服器／Edge 環境使用；禁止 `VITE_` 前綴、前端 bundle、文件或 Git |

`client.ts` 缺少 URL 或可用公開 key 時會拋出設定錯誤。不能把出現登入畫面當成後端全部可用。

目前 AI console 會使用授權取得的 provider key，由瀏覽器送出請求；「畫面遮罩」不等於「金鑰從未到前端」。若新網站要求金鑰不可抵達瀏覽器，需要另外實作／驗證後端代理、權限、額度與稽核，不能宣稱此文件整理已完成該安全改造。不要複製原使用者的 AI 金鑰。

## 7. 新機資料移轉矩陣

| 資料 | 現有邊界 | 換電腦要做什麼 |
| --- | --- | --- |
| 維修、BOM、檔案庫、Data Center 專案、PCB 雲端資料、AI 雲端對話、績效 | 各自的 Supabase table／RPC／Storage 與 RLS | 同後端時核對權限；新產品不預設匯入正式資料 |
| AutoCheck 原始輸入、結果、審查、位址庫 | 瀏覽器本機、依帳號隔離，非跨機即時同步 | 在原瀏覽器匯出備份 ZIP，新機用同功能匯入；另外保留原始 A/B 工程輸入 |
| 部分 Cabinet／L11 設定 | 程式仍有獨立 localStorage key，不等同 `data_center_projects` | 依該功能既有匯出能力處理；未實作移轉者不能只靠登入承諾恢復 |
| 未送出績效草稿與各種本機快取 | sessionStorage／localStorage 或頁面 state | 先儲存／匯出；不得用複製瀏覽器登入儲存區當移轉方案 |
| 上傳失敗的原 File | 本機選取檔案、分頁記憶體與續傳定位 | 保留電腦原檔；完整關頁／重新整理仍需重新選取，不是雲端備份 |
| 私人 API key、帳號密碼、群組保護密碼 | 受控憑證與權限資料 | 不包含在 Markdown 包；本人另行設定或使用核准的密鑰管道 |

AutoCheck ZIP 不包含原始 A/B 工程輸入。ZIP 內位址庫只是當次快照，匯入 session 不會自動取代目前啟用的位址庫，因此啟用中的 library YAML 要另外匯出／匯入並驗證。搬機前實際匯出 ZIP 與 YAML，在隔離的新瀏覽器驗證可匯入；清除瀏覽器資料或移除舊電腦前，不可把未驗證備份當成安全副本。

## 8. 上傳 1 GiB 的必要條件與限制

檔案庫的單檔及現有批次總量上限是 `1073741824` bytes（1 GiB）。這不是所有工作區的共用限制：AutoCheck、AI 附件、圖片、STEP 等各有 validator，不得全部放寬成 1 GiB。

要在新系統真的接受此大小，必須一起核對前端 validator、資料庫 CHECK、`test-plan-files` bucket、Supabase global limit 與方案／代理限制；bucket 上限不能高於 global limit。不能只改 UI 文案，也不能未經授權關閉 spend cap 或升級方案。[Supabase 官方限制說明](https://supabase.com/docs/guides/storage/uploads/file-limits)

非空檔案使用 6 MiB TUS 區塊；成功要有伺服器實際完成證據，再建立應用 metadata。不確定是否完成時保留待重試，不能用進度到 100% 就宣告成功，也不能直接刪除已傳入內容。這輪未做正式 1 GiB 傳輸，新產品必須自行端到端驗證。

先前約 643.7 MiB PDF 的原檔搜尋仍未完成；上傳修復不等於找回檔案。文件包不含那份 PDF，也不宣稱已恢復。

## 9. 獨立部署與驗收順序

1. 在自己的 repo／帳號設定 Pages 或自己選擇的主機；本系統原部署是 GitHub Pages，不是 Netlify 或 NAS 部署腳本。
2. 在自己的 Actions secrets 設定瀏覽器公開 Supabase URL/key，Variables 設 schema 與 realtime flag；不能把 server secret 打進前端。
3. Pages workflow `main.yml` 只發布 `dist`，不會建立資料庫、部署 Edge Functions、匯入公司資料或配置 Storage／Realtime。
4. 先完成隔離後端與安全測試，再發布前端。驗證實際使用者 URL、登入、角色、九工作區入口、深連結、換頁、儲存重開、上下載、備份匯入及錯誤重試。
5. 用兩個不同權限帳號驗證跨帳號隔離、撤權、停用與登出；按鈕隱藏不是安全邊界。
6. 依 UI 規則檢查桌面、390px、平板、橫向、鍵盤與長資料；實機 iPhone Safari／獨立 PWA 要另外驗證，桌面模擬不能代替。
7. PCB 需要 Top／Bottom、旋轉、孔洞、插入深度與儲存重開的實際目視；AI 付費呼叫和大型傳輸先確認費用與授權。

完成紀錄要分列程式 SHA、前端部署、DB／function／bucket 狀態、測試結果、未驗證項及回復方式。不可只憑 Pages 綠燈宣稱整套系統可用。
