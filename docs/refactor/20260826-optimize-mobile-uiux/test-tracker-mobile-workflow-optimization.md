# Test Tracker 手機版工作流程優化建議

## 1. 目標

本文件依 `web-design` skill 將 Test Tracker 的高頻手機任務優化為單手可完成、狀態清楚且不易誤觸的流程，重點涵蓋「找到機台 → 更新測試進度 → 記錄異常／建立問題 → 確認結果」。這是可交付另一位實作者的規格；執行者不必安裝 skill，但應依本文件的元件對照、狀態規則與驗收條件實作。若執行期間需重新做 UI 決策或擴充未涵蓋流程，仍建議安裝 skill 作為 quality gate。

## 2. 現有流程與主要問題

目前實際入口是 `TestProgressTable` 的手機卡片：點機台名稱編輯基本資料，點進度色條開啟 `SystemProgressSheet`，再於測項中更新狀態／進度／備註或開啟通用 `IssueCreateDialog`。`MobileSystemCard` 與 `MobileProgressInput` 沒有被現行頁面引用，屬於舊流程，不應作為本次設計基礎。

| 優先級 | 現況與證據 | 使用風險 | 優化方向 |
| --- | --- | --- | --- |
| P0 | `TestProgressTable.tsx` 以整條進度色帶作為「更新進度」入口，但卡片上沒有明確 CTA。 | 新使用者難以發現主要操作，且機台名稱反而開啟次要的基本資料編輯。 | 卡片加入全寬主按鈕「更新進度」；基本資料編輯移至次要選單。整張卡片不混用多種點擊結果。 |
| P0 | `SystemProgressSheet.tsx` 的 dirty draft 在關閉時直接清除，沒有未儲存確認。 | 現場輸入備註或進度後，誤滑關閉會遺失資料。 | 有未儲存變更時攔截返回、關閉與 swipe-to-dismiss，顯示「繼續編輯／捨棄變更」；成功儲存後才清除 dirty state。 |
| P0 | 「完成此站」會直接以 `Promise.all` 完成所有未完成測項，沒有確認摘要。 | 一次誤觸可改動多筆資料，且未先說明未解問題或失敗項。 | 按鈕顯示將變更的測項數；二次確認列出未完成與未解問題。存在阻擋條件時停用並用文字說明原因。 |
| P1 | Sheet 使用 `h-[calc(100vh-214px)]`，上方站點 tabs 以固定最小寬度水平捲動。 | 瀏覽器工具列／安全區可能遮擋內容，作用中站點也可能在畫面外。 | 改用 `100dvh`、flex 與 `min-h-0`；作用中站點自動捲入視野，顯示左右可捲動提示，或用站點選擇器替代。 |
| P1 | 每個測項預設完整展開狀態、百分比、備註、儲存、問題、計時與工時管理。 | 手機頁面很長，重複控制造成認知負擔，難以快速找到下一個待辦。 | 預設顯示摘要與快速動作，點擊後展開單一編輯器；未完成／異常置頂，已完成項收合。 |
| P1 | 建立問題會開啟完整的通用 `IssueCreateDialog`；附件提示要求 `Ctrl+V`，圖片輸入沒有相機 capture。 | 現場通報欄位過多，手機提示不適用，也無法快速拍照佐證。 | 增加測項專用 quick issue sheet；預填並鎖定機台／站點／測項，支援 `capture="environment"`，進階欄位收合。 |
| P1 | 關鍵失敗主要以 toast 回報。 | toast 消失後無法知道哪個欄位或測項失敗，網路不穩時尤其明顯。 | 保留輸入草稿，在出錯控制旁顯示持久 inline error 與「重試」；toast 只作輔助通知。 |
| P2 | `MobileProgressInput` 使用 32px icon-only 操作，且「問題」只改狀態、沒有建立問題資料。 | 若舊元件日後被誤用，會產生不一致且不可追蹤的流程。 | 刪除或明確 deprecated 未使用元件；所有異常統一走建立／關聯問題的 domain action。 |

## 3. 目標工作流程

```text
篩選／搜尋機台
      ↓
手機機台卡片 ──「更新進度」──→ 全螢幕進度 Sheet
                                      ↓
                         選擇目前站點與待辦測項
                           ↙          ↓          ↘
                       開始計時     更新並儲存    回報異常
                                                   ↓
                                         Quick Issue Sheet
                                                   ↓
                                      建立問題並標記異常
                                                   ↓
                              返回原測項，顯示已關聯問題
```

### 3.1 找到並開啟機台

- 篩選列緊接結果區上方，欄位順序維持「搜尋 → 站點 → 狀態 → 工程師」；排序與檢視切換置於次要工具區。
- 作用中條件 chip 必須一直可見、可個別清除並有「全部清除」，同步 URL query。沒有結果時保留結果容器並顯示 `目前篩選條件沒有符合的機台`。
- 手機卡片第一層只顯示辨識與決策所需資訊：機台名稱、目前／下一站、整體進度、阻擋狀態、負責工程師。
- 「更新進度」是全寬、44px 以上的主 CTA；「編輯機台資料」與其他低頻操作放入有標籤的更多選單。

### 3.2 更新進度

- 開啟全螢幕 Sheet 後，固定 header 顯示機台名稱、目前站點、未儲存狀態與 44×44px 關閉鈕。
- 測項依「異常／被阻擋 → 進行中 → 未開始 → 已完成」排列；已完成區預設收合但顯示數量。
- 每列摘要顯示測項名稱、狀態、進度、最後更新者／時間與已關聯問題。整列至少 44px 高，不以顏色作唯一狀態訊號。
- 點擊摘要只展開一個測項編輯器；提供「開始」、「完成」、「回報異常」快速動作。百分比與狀態變更需維持 domain 規則，例如完成即為 100%。
- 一般更新可逐項明確儲存；若改成批次儲存，底部 sticky CTA 必須顯示「儲存 N 項」，並避開 safe-area。無論哪一種都要顯示 saving、saved、error 與可重試狀態。

### 3.3 校正測試時間

- 「開始／完成」仍可用按鈕點擊時間自動計時，但每個測項都要提供「校正時間」，讓事後補登者手動輸入實際開始與結束時間。
- 日期與時間在手機上使用原生輸入並分開呈現，觸控目標至少 44px；可快速套用現在時間，但不得只提供預設按鈕而無法精確輸入。
- 開始、結束、時區轉換、耗時計算與驗證必須由 shared utility 處理，Desktop／Mobile 只調整輸入結構，不得各自維護計算公式。
- 輸入時即時顯示校正後耗時；結束早於開始、只有結束時間或格式無效時顯示 inline error 並禁止儲存。
- 校正結果需持久寫回 `started_at`、`completed_at` 與重新計算的 `actual_hours`；只有開始時間視為進行中，具有結束時間則遵守既有完成與未解問題 guard。

### 3.4 建立問題

- 從測項進入時使用 quick issue sheet，而非直接呈現完整問題表單。標題可由「機台＋站點＋測項」預填；上下文以唯讀區塊顯示，避免建立到錯誤機台。
- 第一屏只保留：問題描述（必填）、嚴重度／優先級、照片或附件，以及主 CTA「建立問題並標記異常」。負責人與其他進階欄位放入「更多設定」。
- 圖片附件支援開啟後鏡頭、相簿與檔案；顯示檔案大小／格式限制、上傳進度、失敗原因、移除與重試。手機上不顯示 `Ctrl+V` 指示。
- 建立失敗時保留所有草稿並在對應區塊顯示錯誤；成功後關閉 quick sheet、返回原測項，顯示問題編號、狀態與「查看問題」。避免讓使用者自行重新定位。
- 完成或關閉已關聯問題前，若 domain 規則禁止將測項設為 Done，應停用該動作並顯示具體原因與可前往處理問題的連結。

## 4. 畫面結構規格

### 機台卡片

1. Header：機台名稱＋文字狀態 badge；右側更多選單。
2. Body：目前站點／下一站、負責人、可讀的進度文字與進度條。
3. Alert：僅在阻擋或未解問題時顯示，包含問題數與可進入的文字連結。
4. Footer：全寬主按鈕「更新進度」。不要要求使用者點擊沒有文字的進度條。

### 進度 Sheet

1. Sticky header：返回／關閉、機台、站點、儲存狀態。
2. Station navigation：目前項目一定可見，支援鍵盤與自動 `scrollIntoView`；若站點多，優先採 selector。
3. Summary：完成數、進行中數、異常數，以及有防呆的「完成此站」。
4. Scrollable task list：只讓內容區捲動，不建立巢狀全頁捲動。
5. Sticky action：僅在存在未儲存變更時出現，避開 bottom safe-area。

### Quick Issue Sheet

1. Sticky header：`回報異常`＋機台／站點／測項摘要。
2. Body：描述、優先級、照片／附件、可展開的更多設定。
3. Inline states：欄位驗證、附件上傳、送出錯誤與離線狀態。
4. Sticky footer：次要「取消」與主要「建立問題並標記異常」。

## 6. 必須涵蓋的狀態與防呆

- 初次載入、局部重新整理、無測項、無篩選結果、離線、逾時、401/403、單筆儲存失敗、部分批次失敗及完整成功。
- 未儲存內容關閉、瀏覽器返回、切換站點、切換機台及 Sheet swipe dismiss。
- 計時器已在其他測項運作、開始失敗、停止失敗、完成後工時寫入失敗。
- 校正時間只有開始、只有結束、跨日、結束早於開始、清空時間與校正儲存失敗；畫面耗時必須與持久化的 `actual_hours` 一致。
- 問題附件上傳中／失敗、建立問題失敗、重複送出、問題建立成功但進度狀態更新失敗。
- 「完成此站」包含未完成測項、未解問題、權限不足、部分 API 失敗；批次結果要逐筆可追蹤，不只顯示單一 toast。
- 使用者可見狀態統一使用繁中；內部 enum（例如 `Not Start`、`On-going`、`Done`）不得直接裸露於介面。

## 7. 建議交付順序

1. **PR 1 — 共用基礎：** Sheet 44×44px、dvh/safe-area、focus return、inline mutation state 與 dirty-close guard。
2. **PR 2 — 進度入口與資訊架構：** 手機機台卡片 CTA、測項排序／收合、作用中站點導覽與一致的繁中狀態。
3. **PR 3 — 安全更新：** 單項儲存回饋、計時狀態，以及「完成此站」確認、阻擋與部分失敗處理。
4. **PR 4 — Quick Issue：** 抽取共用問題建立邏輯，完成相機附件、草稿保留、inline error 與返回原測項。
5. **PR 5 — 清理與回歸：** 移除舊手機元件，加入 320／375／390／430px screenshot 與核心 workflow E2E 測試。

## 8. 驗收條件

- 使用者從手機機台卡片可在一次明確點擊內進入更新流程，不需要猜測進度條可點擊。
- 320px 寬與 200% zoom 下沒有整頁水平捲動；站點導覽若需水平捲動，作用中站點可見且有可捲動提示。
- 所有觸控目標至少 44×44px；狀態具有文字，focus 順序符合畫面順序，關閉後 focus 回到原「更新進度」按鈕。
- 有未儲存變更時，關閉、返回、滑動退出與切換上下文都不會無提示遺失內容。
- 手動校正開始／結束時間後立即顯示正確耗時；錯誤區間無法送出，日期／時間輸入在 320px 與軟鍵盤開啟時仍可操作。
- 「完成此站」在執行前顯示影響筆數與阻擋原因；部分失敗可辨識、可重試，不會錯誤顯示整批成功。
- 建立問題時上下文已預填，使用者只輸入必要資訊即可拍照並送出；失敗不清空草稿，成功後原測項立即顯示關聯問題。
- 軟鍵盤、瀏覽器工具列與 Home Indicator 不遮住目前欄位或主要 CTA；旋轉螢幕後輸入內容與展開狀態保留。
- Test Tracker 篩選、作用中 chip、URL 與空結果文字完整符合 `AGENTS.md`，且排序／檢視工具不打亂主要篩選順序。

## 9. 驗證建議

- 元件測試：dirty-close guard、狀態／百分比規則、問題阻擋、批次部分失敗、URL filter parsing 與全部清除。
- E2E：搜尋機台 → 更新單一測項 → 建立問題並附照片 → 返回確認關聯 → 解決後完成測項；另測離線重試與未儲存離開。
- 視覺回歸：320、375、390、430px，涵蓋預設、鍵盤開啟、長機台名稱、多個 chip、error、empty 與 loading。
- 手動可及性：只用鍵盤操作、VoiceOver／TalkBack 名稱與順序、200% zoom、reduced motion、淺色／深色對比。
